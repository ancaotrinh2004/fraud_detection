# Fraud Detection ML Design

Follows the structure of `04.1_ml_design_example.md`, built on the Gold data and feature tables from Sessions 02 and 03.

---

## 1. Goal

Build a fraud-scoring system on top of the Gold feature tables.

**Task:** predict whether a transaction is fraudulent at the time it occurs.

**Why:** fraud causes direct financial loss; the task uses both offline 90-day batch features and near-real-time 30-minute streaming features; the label `is_fraud` is deterministically derived (≥2 of 4 conditions) so ground truth is consistent; and Session 03's amount drift gives a natural retraining trigger linking drift monitoring to the ML lifecycle.

---

## 2. Prediction Setup and Modeling Plan

**Prediction setup**
- Entity: `transaction_id`; Label: `is_fraud` (1=fraud, 0=legit).
- Prediction time: feature snapshot at the transaction's `event_ts`.
- Class balance: ~90% legit / ~10% fraud.

**Training data input**
- Table `gold_fraud.ml_fraud_training` (Session 03), one row per `transaction_id`.
- **17 model features** = 15 stored + 2 derived: six `f_customer_*_90d`, five `f_stream_*`, `txn_amount`, `txn_hour`, `is_declined_txn`, `is_foreign_txn`, plus derived `txn_amount_ratio` (`txn_amount / f_customer_avg_txn_amount_90d`) and `is_night_txn` (`txn_hour ∈ [1,4]`). The four label conditions each map to a feature, guaranteeing learnable signal.

**Modeling decisions**
- Split: **fraction-based time split** — earliest 70% train / next 15% val / last 15% test, boundaries computed from actual timestamps (adapts to date range). Time order mirrors production (score future, unseen transactions).
- Model: **XGBoost** — handles class imbalance via `scale_pos_weight`, tolerates sparse streaming features, gives feature importances cheaply. Swappable behind a `BaseClassifier` strategy interface.
- Imbalance: `scale_pos_weight = neg/pos` computed dynamically (~9 at 10% fraud), recalibrated each retrain.
- Metrics: **PR-AUC** primary (right for severe imbalance); secondary **F1 @ 0.5**, Precision, Recall. Acceptance: PR-AUC ≥ 0.70 to promote.
- **Achieved:** registered production model `fraud-xgboost` PR-AUC **0.8178**, F1 0.8506.

**Assumptions**
- Objective: minimise fraud loss (false negatives) while controlling false positives; scores drive block / step-up-auth, with a human review queue for borderline scores (0.4–0.7).
- Explainability and per-request governance are out of scope this phase (feature importances logged per model version).

**SLA targets**

| Target | Value |
|---|---|
| Online inference latency | p95 < 50 ms (achieved: single-digit ms on Kind) |
| Batch score freshness | < 24 h |
| Stream feature freshness | < 5 min |
| Batch feature freshness | < 60 min |

## 3. High-Level ML Design

End-to-end flow:
1. Build/validate `ml_fraud_training` from Gold inputs (Session 03).
2. **Training pipeline**: build dataset → train → evaluate → log to **MLflow** → register in MLflow Model Registry.
3. **Retrain-trigger pipeline**: drift / quality trigger → retrain → compare candidate vs Production → promote or rollback.
4. **Batch scoring**: score transactions daily → `gold_fraud.ml_fraud_scores`.
5. **Online inference**: a **KServe** custom model serving the Production model for the real-time channel.
6. Monitor logs (Loki), metrics (Prometheus/Grafana), traces (Jaeger).

### 3.1 Security Decision
- Gold tables accessible to the `fraud_user` PostgreSQL role; production inference reads via a read-only path.
- Model artifacts live in the MinIO bucket `mlflow-artifacts` behind the MLflow tracking server; credentials (`POSTGRES_PASSWORD`, `AWS_*`/`MINIO_*`, `MLFLOW_*`) are Kubernetes Secrets referenced in Airflow and the InferenceService — never hardcoded.
- Coursework cluster is single-tenant Kind; the InferenceService runs as a ClusterIP behind the Knative/Istio mesh (no public ingress).

### 3.2 Resilience Decision
- Airflow jobs retry up to 3× with exponential backoff (`configs/pipeline_config.yaml`).
- Batch scoring is partition-idempotent (`ON CONFLICT (transaction_id) DO UPDATE`) — safe re-runs/backfills.
- Promotion is guarded: the candidate must beat Production before `transition_model_version_stage` archives the old version; otherwise the current Production model stays. Rollback re-promotes a prior version.

### 3.3 Training/Inference Pattern Decision
- **Training:** weekly schedule (Sun 02:00 UTC) + drift-triggered retraining.
- **Inference:** precomputed batch scores (primary) + online KServe endpoint (secondary, real-time POS/e-commerce).
- **Trade-off:** batch covers bulk authorisation review; the online endpoint serves low-latency real-time checks. Two paths add ops cost but match the dual-channel fraud use case.

### 3.4 Storage Decision
- Bronze/Silver: Delta Lake in MinIO (`s3://bronze`, `s3://silver`).
- Gold features/labels/scores: PostgreSQL `gold_fraud`.
- **Model artifacts + experiment tracking: MLflow** — tracking server (Postgres backend store + MinIO `mlflow-artifacts` artifact store); models logged with `mlflow.sklearn.log_model`, physical path resolved via `get_logged_model().artifact_location`.
- **Model registry: MLflow Model Registry** (registered model `fraud-xgboost`, stages `Staging`/`Production`) — replaces the earlier Postgres registry table.
- Logs: structured JSON → Loki; traces → Jaeger.

### 3.5 Routing/Gateway Decision
- KServe + Knative provide the serving gateway: the `InferenceService` `fraud` exposes the predictor through `knative-local-gateway` (Istio). Model name `fraud-predictor`; endpoint `POST /v2/models/fraud-predictor/infer` (open-inference-protocol **V2**).
- Versioned rollout: a new model version is promoted in the MLflow registry and the predictor reloads Production; image rollouts use Knative revisions. Canary/blue-green is available via Knative traffic splitting (not enabled in coursework).

## 4. Low-Level ML Design

Five core classes (+ the KServe serving wrapper), each applying an [ML design pattern](https://github.com/msaroufim/ml-design-patterns).

| Class | Pattern | Why |
|---|---|---|
| `TrainingDataService` | Pipeline | read → validate → split → handle-missing, each step feeds the next |
| `ModelService` | Strategy + Learner | swappable `BaseClassifier`; unified `train()/evaluate()/save_model()` over MLflow |
| `ModelRegistryService` | Pipeline | register → promote → rollback state machine over MLflow registry stages |
| `ScoringService` | Iterator + Pipeline | `score_batch` chunks rows (Iterator) then score → write (Pipeline); `score_online` for single requests |
| `MonitoringService` | Observer | publishes pipeline/model metrics to the Pushgateway and evaluates retrain triggers — a side-effect listener, not in the train path |
| `FraudModel(kserve.Model)` | Adapter | wraps the artifact + feature lookup behind KServe's `load()/predict()` V2 contract |

```python
class TrainingDataService:                 # Pipeline
    def read_training_table(self, engine) -> pd.DataFrame: ...
    def validate_schema(self, df) -> None: ...
    def split_by_time(self, df) -> tuple[pd.DataFrame, pd.DataFrame, pd.DataFrame]: ...

class ModelService:                         # Strategy + Learner (MLflow-backed)
    def __init__(self, cfg, classifier: BaseClassifier | None = None):
        self.classifier = classifier or XGBoostClassifier()
    def train(self, train_df) -> object: ...
    def evaluate(self, model, test_df) -> dict: ...           # pr_auc, f1, precision, recall, threshold
    def save_model(self, model, metrics, model_version) -> str:
        # mlflow.sklearn.log_model(name="model"); returns artifact_location (s3://mlflow-artifacts/...)
        ...
    def load_model(self, model_uri: str) -> ModelArtifact: ...  # models:/fraud-xgboost/Production

class ModelRegistryService:                 # Pipeline over MLflow registry
    def register(self, run_id, metrics, artifact_path, train_rows, status="candidate") -> str: ...
    def get_production_version(self) -> dict | None: ...        # get_latest_versions(stages=["Production"])
    def promote(self, version) -> None: ...                     # transition + archive_existing_versions=True
    def rollback(self, previous_version) -> None: ...

class ScoringService:                       # Iterator + Pipeline
    def score_batch(self, artifact, df, chunk_size=5_000) -> pd.DataFrame: ...
    def write_scores(self, score_df, engine) -> None: ...       # upsert ml_fraud_scores
    def score_online(self, artifact, features: dict) -> dict: ...

class FraudModel(kserve.Model):             # Adapter to open-inference-protocol V2
    def load(self) -> bool: ...                                 # load MLflow Production model + engine
    def predict(self, payload, headers=None) -> dict: ...       # V2: fetch features → score → outputs
```

## 5. Infrastructure Decision

**Choice: Kubernetes (existing Kind cluster).** Reuses Airflow, MinIO, PostgreSQL, MLflow, and the KServe stack (cert-manager / Istio / Knative / KServe) already deployed.

| Workload | CPU req | Mem req | Notes |
|---|---|---|---|
| Airflow worker (train/score via KPO) | 200m–500m | 1–2 Gi | XGBoost on ~1.44M rows fits in memory |
| Inference predictor (KServe custom container) | 500m | 512 Mi | stateless; loads Production model at startup, `imagePullPolicy: Always` |
| MLflow / MinIO / PostgreSQL | shared | — | existing |

**Storage:** MLflow artifacts ~50 MB/version in `mlflow-artifacts`; `ml_fraud_scores` ~144 MB; training data ~800 MB.

**Scaling:** weekly training runs on one worker (~5–10 min). The predictor scales via Knative (scale-to-N on concurrency); retrain overlaps the weekly schedule at most once, bounded by worker memory limits.

## 6. Pipeline Design

Bronze/Silver/Gold and feature pipelines (Session 02/03) are reused as upstream dependencies. ML DAGs run as `KubernetesPodOperator`/`@task` jobs on the `ancaotrinh/fraud-airflow` image.

**Pipeline A — Training** (`dag_ml_train`, weekly `0 2 * * 0`)
1. build dataset — read `ml_fraud_training`, validate, time-split.
2. train — XGBoost with dynamic `scale_pos_weight`, inside `mlflow.start_run()`.
3. evaluate — PR-AUC / F1 / Precision / Recall; fail if PR-AUC < 0.70.
4. register — `mlflow.sklearn.log_model` → `ModelRegistryService.register` → promote to `Production` if it beats current.

**Pipeline B — Batch Scoring** (`dag_ml_batch_score`, daily `0 5 * * *`)
1. load Production model from MLflow (`models:/fraud-xgboost/Production`). *(Requires `AWS_*` + `MLFLOW_S3_ENDPOINT_URL` env to pull artifacts from MinIO.)*
2. score transactions joined with the latest feature snapshot.
3. upsert `gold_fraud.ml_fraud_scores (transaction_id, fraud_score, model_version, score_ts)` — idempotent.

**Pipeline C — Retrain Trigger** (`dag_ml_retrain_trigger`, daily `0 7 * * *`)
1. check drift — sustained critical PSI (≥0.20) / drifted-feature count from `feature_drift_alerts`.
2. check model quality — F1 on a held-out slice vs the registered baseline.
3. trigger `dag_ml_train` if needed.
4. promote candidate vs Production, else keep/rollback.

## 7. CI/CD Pipeline Design

CI/CD is **3 merged Jenkinsfiles** (CI + CD per track) in `jenkins/`, run by Jenkins on the Kind cluster. Each stage is guarded by `when { changeset "..." }`; an empty changeset on `main` (or `FORCE_DEPLOY=true`) runs all CD stages. CI installs the test env from `requirements.txt` (mlflow, sklearn, xgboost, …; `kserve` is stubbed in tests). **262 tests** total (unit + integration).

**Track A — Data/ML** (`Jenkinsfile.track_a`)
- CI: ruff lint, `pytest tests/unit` + `tests/integration`, DAG import validation.
- CD (main): build+push `ancaotrinh/fraud-airflow:<sha>` → `helm upgrade airflow 1.21.0`; on `dags/**` update the `airflow-dags` ConfigMap and restart **dag-processor + scheduler + worker** (subPath mounts don't auto-refresh, and KPO env_vars live in the DAG); on `configs/pipeline_config.yaml` update `fraud-pipeline-config` and restart workers.

**Track B — Inference** (`Jenkinsfile.track_b`)
- CI: ruff lint, unit tests, V2 contract test (`POST /v2/models/fraud-predictor/infer`), in-process **load test** driving `FraudModel.predict` (p95 < 500 ms).
- CD (main): `docker build -f infra/docker/inference/Dockerfile` → push `ancaotrinh/fraud-inference:<sha>` → `kubectl patch inferenceservice fraud`; wait Ready; smoke test (`/v2/health/ready` + a V2 infer). Rollback re-applies the last-good manifest.

**Track C — IaC** (`Jenkinsfile.track_c`)
- CI: helm lint/template (monitoring, airflow, datahub), `kubectl --dry-run` over `infra/k8s/**` (incl. `fraud-drift-alerts.yaml`, `grafana-fraud-dashboard.yaml`), DAG ConfigMap reference check.
- CD (main): apply secret / net-istio / pushgateway / ServiceMonitor / **drift PrometheusRule + Grafana dashboard**; `helm upgrade` kube-prometheus-stack **85.2.0**, datahub **1.0.0** (prereq 0.3.0), airflow 1.21.0; post-apply health checks. Rollback via `helm rollback`.

Promotion flow: PR (CI) → merge to `main` (CD to the cluster). Model promotion (Staging→Production) is handled in the MLflow registry by Pipeline A/C.

## 8. Monitoring

**Data drift** — `dag_drift_monitor` computes weekly PSI for 11 features + the prediction score; pushes `fraud_drift_psi_*` to the Pushgateway. Alerting is **rule-based**: the `fraud-drift-alerts` PrometheusRule fires `FraudFeatureDriftWarning` (PSI ≥ 0.10) / `FraudFeatureDriftCritical` (≥ 0.20) / `FraudDriftMonitorFailed`, and Alertmanager routes `category: drift` → **Discord** (native `discord_configs`). No alerting in pipeline code.

**Prediction drift** — daily `fraud_score` distribution in `ml_fraud_scores` (PSI of the score is monitored alongside the features).

**Label drift** — weekly fraud rate in `fact_transaction` (expected ~10%).

**Infra** — logs (structured JSON → Promtail → Loki), metrics (Prometheus / kube-prometheus-stack), traces (OTel spans `fetch_features` / `score_model` → Jaeger, service `fraud-predictor`). Inference metrics come from **KServe's built-in `/metrics`** (`request_predict_seconds` histograms) scraped via a `ServiceMonitor` — not a FastAPI instrumentator.

**Grafana** — the `Fraud Detection — Overview` dashboard (`infra/k8s/grafana-fraud-dashboard.yaml`, sidecar-loaded) shows: drift run status + per-feature PSI bars; inference `up`, predict p50/p95/p99 latency, request rate, memory; and model PR-AUC/F1/Precision/Recall (populate after a train run). DataHub captures dataset lineage.

| Signal | Threshold | Action |
|---|---|---|
| Feature PSI | ≥ 0.20 (critical) | Discord alert + retrain trigger |
| F1 drop | > 5% vs baseline | retrain trigger |
| Drift run status | `fraud_drift_run_status == 0` | Discord alert (pipeline failed) |
| Inference p95 | > 50 ms | scale predictor |

## 9. Retraining Strategy

**Scheduled:** weekly (Sun 02:00 UTC), rolling training window.

**Triggered:** `dag_ml_retrain_trigger` fires on sustained critical feature drift or an F1 drop > 5% vs the registered baseline.

**Rules:**
1. Rebuild `ml_fraud_training` on the latest window.
2. Train a candidate (same hyperparameters; `scale_pos_weight` recalibrated to current class ratio) inside an MLflow run.
3. Evaluate on the most recent test slice.
4. Compare candidate vs Production PR-AUC.
5. **Promote** (registry stage → Production, archive previous) if candidate ≥ Production − 0.01; else **keep/rollback**.
6. MLflow retains prior versions for rollback.
