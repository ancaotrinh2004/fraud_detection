# Fraud Detection Data Generator

## 1. Domain Overview

This project simulates a mid-size digital payment platform operating in Vietnam and Southeast Asia. The generator produces:

- Offline historical/reference data (Parquet) — customers, cards, merchants, transactions
- Streaming real-time events (JSON) — login / OTP / payment behaviour on a Kafka topic

The goal is to support downstream ingestion, transformation, and feature engineering while intentionally injecting realistic data quality and processing challenges. The dataset trains and evaluates a fraud detection model (Section 04).

---

## 2. Offline Dataset Design

### 2.1 Offline Tables

| Table | Grain | Key Columns |
|---|---|---|
| customers | one per customer | customer_id, signup_ts, country, city, risk_segment, kyc_status (verified\|pending\|failed), marketing_opt_in |
| merchants | one per merchant | merchant_id, merchant_name, category, country, city, is_active, created_ts |
| cards | one per card | card_id, customer_id, card_type (credit\|debit\|prepaid), issuing_bank, card_country, issued_ts, expiry_ts, is_active |
| transactions | one per transaction | transaction_id, customer_id, card_id, merchant_id, transaction_timestamp, created_ts, amount, currency (VND\|USD\|SGD\|THB), transaction_status (approved\|declined\|pending\|reversed), city, device_fingerprint*, ip_country*, is_fraud |

`device_fingerprint` and `ip_country` (*) exist only after `schema_change_date = 2025-07-01`. `is_fraud` (1=fraud, 0=legit) is the ML label — generated by the rule in Section 04, target rate 10%.

### 2.2 Offline Data Problems

**Compulsory:**
- **Geographic skew**: 80% of transactions from the top 5 cities (HCMC, Hanoi, Da Nang, Can Tho, Hai Phong); 75% of merchants in the top 3 categories.
- **High cardinality**: transaction_id / customer_id / card_id are near-unique (100k customers, 15k merchants, 130k cards).
- **Schema evolution**: pre-2025-07-01 transactions (~60% of history) lack `device_fingerprint` + `ip_country` (fraud-signal columns added later).

**Optional chosen:** 2% duplicate rate in `transactions` (payment-gateway retries — same `transaction_id`/`amount`/`transaction_timestamp`, different `created_ts`).

**Output:** Parquet partitioned by `transaction_date`.

## 3. Streaming Dataset Design

### 3.1 Event Stream Schema

Single unified topic `fraud.events.raw` with an `event_type` field.

Key columns:
- `event_id`, `event_type` (login | card_check | transaction_attempt | transaction_approved | transaction_declined | otp_request | otp_failed)
- `event_timestamp`, `created_ts` (event time vs ingestion time)
- `customer_id`, `session_id`, `device_type` (mobile|web|atm|pos), `ip_country`
- `merchant_id`, `card_id`, `amount`, `failure_reason` (nullable — payment events only)

Events are **session-anchored**: each offline transaction emits a correlated mini-session (login → otp → attempt → approved/declined). Fraud transactions get extra `otp_failed` × 1–3 and declined-probe events in the 30 min before, so the streaming features below carry real predictive signal (mirrors the e-commerce sample's funnel linkage). Volume ≈ 34M events over 180 days.

### 3.2 Streaming Data Problems

**Compulsory:**
- **Bursts**: 50 events/min baseline → 2,000 events/min (40×) in two 20-min windows: 12:00–12:20 and 22:00–22:20 (night fraud window).
- **Late arrivals**: 15% of events have `created_ts` 5–60 min later than `event_timestamp` (mobile buffering / weak network).

**Optional chosen:** 1.5% duplicate events (mobile retries; same `event_id` within 1–3 min). Dedup key = `(event_id, event_timestamp)`.

**Output:** newline-delimited JSON.

## 4. Feature Engineering

**Offline (90-day rolling windows, per customer):**
- `f_customer_total_txn_90d` — transaction count
- `f_customer_avg_txn_amount_90d` — average amount
- `f_customer_distinct_merchants_90d` — merchant diversity
- `f_customer_decline_rate_90d` — declined ratio
- `f_customer_foreign_txn_ratio_90d` — `ip_country ≠ card_country` ratio
- `f_customer_night_txn_ratio_90d` — 01:00–04:00 ratio

**Streaming (rolling windows):**
- `f_stream_otp_failed_count_30m` — OTP failures (30 min)
- `f_stream_decline_count_30m` — declines (30 min)
- `f_stream_txn_velocity_1h` — attempt count (1 h)
- `f_stream_new_merchant_flag` — merchant unseen in 90-day history (point-in-time)
- `f_stream_burst_activity_flag` — event in a burst window (point-in-time)

Offline + streaming features merge into a unified table keyed by `customer_id` + `event_ts`, refreshed every 15 minutes — the direct input to ML training (Section 04). The four label conditions (amount anomaly, cross-border, night-time, declined) each map 1:1 to a feature, guaranteeing learnable signal.

## 5. Generator Configuration

```yaml
# Entity volumes
n_customers: 120000
n_merchants: 15000
n_cards: 130000            # ~1.3 cards per customer
days_history: 180
avg_txn_per_customer: 12

# Fraud label
fraud_rate: 0.10
fraud_label_min_conditions: 2   # >=2 of 4 conditions → is_fraud=1

# Skew
skew_city_ratio: 0.80
skew_category_ratio: 0.75
top_cities: [Ho Chi Minh City, Hanoi, Da Nang, Can Tho, Hai Phong]

# Offline problems
duplicate_rate_offline: 0.02
schema_change_date: "2025-07-01"

# Streaming
base_events_per_min: 50
burst_multiplier: 40
burst_windows: ["12:00-12:20", "22:00-22:20"]
late_arrival_rate: 0.15
late_delay_min_max: [5, 60]
duplicate_rate_stream: 0.015

random_seed: 42
```

## 6. Deliverables

1. **Generator code** (`src/generator/generate_data.py`) — parameterized by `configs/generate_config.yaml`.
2. **Offline outputs**: `customers.parquet`, `merchants.parquet`, `cards.parquet`, `transactions/` (partitioned).
3. **Streaming output**: `fraud_events.json` (newline-delimited).
4. **Quality report** covering: city/category skew %, cardinality per key, schema-evolution null % pre/post 2025-07-01, duplicate rate before/after dedup, streaming burst/late/duplicate rates, and confirmed 10% fraud rate.
5. **Write-up**: optional-problem choices and feature/label rationale.

---

## 7. Implementation Tips

- Use a deterministic `random_seed` for reproducible labels and distributions.
- Dedup keys: offline `(transaction_id, created_ts)`; streaming `(event_id, event_timestamp)`.
- The 10% fraud rate is an intentional, elevated choice (industry is 0.5–3%) so the ~1.4M-row dataset yields a stable PR-AUC; natural pre/post-July rates are ~3% / ~11%, calibrated down to 10% while preserving >90% of the deterministic signal.
